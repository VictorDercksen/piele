# The Pavilion API

FastAPI backend for The Pavilion. Its first league is Piele. Routes live under `/v1`:

- `GET /v1/health` reports the environment and database status.
- Account routes, requiring a Supabase access token (`Authorization: Bearer …`) but no league (`app/routers/account.py`):
  - `GET /v1/me`: `{userId, photoUrl, isAdmin, lastLeagueId, leagues: [{id, slug, name, timezone, emblemPreset, emblemUrl, accentColour, competition: {id, name, shortName}, seasonName, inSeason, memberId, displayName, isCaptain, favouriteTeamId}]}`. It first claims every name reserved for the verified sign-in email, in every league (one `membership.claimed` audit event and `member_joined` feed entry per league). Leagues the account belongs to come first, by name; the admin then gets every other active league with `memberId`, `displayName` and `favouriteTeamId` null. Every league description (these entries, the join page's league and the league-scoped `me`) carries `emblemPreset` (a preset key, drawn by the web from `assets/images/emblems/<key>.svg`) and `emblemUrl` (a signed URL, uploaded emblems only, valid for `LEAGUE_EMBLEM_URL_TTL_SECONDS`, default a day); both null means no emblem.
  - `GET /v1/join/{code}`: `{league: {id, slug, name, timezone, emblemPreset, emblemUrl, accentColour, competition, seasonName}, alreadyMember, unclaimed: [{id, displayName, fullName}]}`, where `unclaimed` holds that league's unclaimed names that are not reserved, plus the one reserved for the caller's verified email. `404 unknown_join_code` when no active league has the code (case-insensitive).
  - `POST /v1/join/{code}` with `{membershipId}` claims that name and returns the league-scoped `me` document. `409 already_member` when the account already has an active membership there, `409 withdrawn_member` when it left the league, `409 name_taken` when the name is claimed or not in that league, `403 reserved` when it is reserved for another address. The favourite team is copied from the account's most recently updated membership in another league on the same competition.
- League endpoints under `/v1/leagues/{leagueId}` (`app/routers/league.py`), requiring an active member of that league or the admin: an unknown or archived league is `404 unknown_league`, anyone else `403 not_a_member`. `GET .../me` returns `{leagueId, slug, leagueName, timezone, emblemPreset, emblemUrl, accentColour, competition: {id, name, shortName}, seasonName, inSeason, memberId, displayName, isCaptain, isAdmin, administers, joinCode, favouriteTeamId, photoUrl, notificationsReadAt, notificationsReadKeys}` (the admin viewing a league they do not belong to gets `memberId` null, `displayName` `"Admin"`, `isCaptain` false; `joinCode` is filled only when `administers`, and null there means joining is closed); `PUT .../me/last` (204) records the league as the account's last opened; `POST .../me/photo/uploads` (account-wide photo upload grant) and `PUT .../me/profile` (the favourite team on this membership, one of the competition's clubs, else `422 unknown_team` "Choose a team from this competition.", and the account-wide photo); `PUT .../me/notifications` (what the member has read in this league's notifications panel: a high-water mark `readAt` and up to 200 `readKeys` read individually above it, merged so a stale device never moves the mark back); `GET .../members` (active members, each `{id, displayName, fullName, status, claimed, inSeason, email, leftAt, withdrawalReason}`, `email` only for the captain or admin; `?include=withdrawn` adds removed members for the captain or admin and is ignored for everyone else), `POST .../members`, `PATCH .../members/{id}` (reserve a name for an email) and `POST .../members/{id}/release` (captain or admin); `POST .../members/{id}/withdraw` with `{reason}` (1 to 500 characters; captain or admin, 204): in one transaction the membership and its active season membership are withdrawn (`left_at`, `withdrawal_reason`, `effective_to`), the member's open and pending-deadline duties are voided with the reason "Member withdrawn" (their pending evidence superseded), standings, evidence and marks stay stored, the feed says "<name> left the clubhouse." (`member_left`) and the audit trail records `membership.withdrawn` with the reason; an unclaimed name with no duties, standings, evidence or other references is deleted outright instead (`membership.deleted`, no feed entry). `409 captain_membership` for the captain, `409 own_membership` for the caller's own membership, `404 unknown_member`, `409 already_withdrawn`. A withdrawn member's next request to the league is `403 not_a_member`, `GET /v1/me` no longer lists it, and the member is left out of the team sheet, standings, duties, marks and the join page's names. `POST .../members/{id}/reinstate` (captain or admin, 204; `409 not_withdrawn`) makes the membership active again and enrols the member in the active season with a new season membership (the withdrawn one keeps its `effective_to`), with the feed entry "<name> is back." (`member_returned`); the earlier standings and marks count again. `POST .../emblem/uploads` with `{contentType, sizeBytes}` (captain or admin, 201 `{bucket, path, token}`; `image/jpeg`, `image/png` or `image/webp`, else `422 not_an_image`, at most `LEAGUE_EMBLEM_MAX_BYTES`, default 1 MiB, else `422 too_large`) and `PUT .../appearance` with any of `{emblemPreset, emblemPath, accentColour}` (captain or admin; a field left out is untouched, null clears it; returns `me`): a preset is one of `oak`, `anvil`, `lantern`, `compass`, `chevron`, `crown`, `wave`, `star` (stored as `preset:<key>`), an upload must be a finished object under `emblems/<league id>/` from the grant (`422 unknown_upload`) whose first bytes match its type and whose size is within the limit (`422 invalid_emblem`, and the object is removed); preset and path together, or an unknown preset, are `422 invalid_emblem`; the accent colour is `#rrggbb` (`422 invalid_accent_colour`). Setting one emblem clears the other, a replaced upload is deleted from Storage, the audit trail records `league.appearance_updated`, and the feed says "The <league> emblem was updated." (`emblem_updated`) only when the emblem changed. `POST .../join-code/rotate` (captain or admin, 200 `{joinCode}`: twelve new hex characters; the old code stops working and a closed league opens) and `DELETE .../join-code` (204, closes joining) write `league.join_code_rotated` or `league.join_code_closed` to the audit trail (without the code) and nothing to the feed; `GET .../duties?round=`, `POST .../duties` and `POST .../duties/{id}/void` and `POST .../duties/{id}/reset-clock` (captain or admin), `GET .../duties/default-deadline`; `GET .../marks`; `GET .../standings?round=` (Superbru round points, ranked; tied points share a rank) and `PUT .../rounds/{round}/standings` (captain or admin; replaces the round's table from the pool results, body `{"standings": [{"memberId", "points"}]}`, points in steps of 0.1); `POST .../evidence/uploads` (upload grant), `POST .../evidence` (publish a submission), `POST .../evidence/links/{id}/decision` (an uninvolved captain or admin), `GET .../evidence/assets/{id}/playback`; `GET .../feed?round=`. Captain routes answer `403 captain_only` to other members. Round numbers run from 1 to the last round of the season's competition (21 for the URC); others are `422 unknown_round`. Every mutation writes its audit event and feed entry in the same transaction. See `app/league/`.
- Management centre routes under `/v1/admin` (`app/routers/admin.py`), for the admin only (`admin_dependency`; everyone else, captains included, gets `403 admin_only` "Only the admin can do this."). No league context comes from the dependency: each operation sets the context of the league it reads or writes. Leagues are described as `AdminLeague`: `{id, slug, name, timezone, status, emblemPreset, emblemUrl, accentColour, joinCode, competition: {id, name, shortName}, season: {id, name, status} | null, captain: {memberId, displayName, claimed} | null, counts: {members, claimed, inSeason, withdrawn}, myMemberId, createdAt}` (`counts`: active memberships, those claimed, those enrolled in the active season, withdrawn memberships; `myMemberId`: the admin's own active membership, or null).
  - `GET /v1/admin/leagues`: every league, archived included, active first, then by name.
  - `POST /v1/admin/leagues` (201 `AdminLeague`) with `{name, slug, timezone?, competitionId, seasonName, members: [{fullName, displayName}], captainDisplayName, captainEmail, emblemPreset?, accentColour?, addMe?}` calls `service.create_league` (audit `league.created` with `actor_label = 'admin'`); its refusals pass through: `422 invalid_slug` (format or a reserved word such as `manage`), `409 slug_taken`, `422 unknown_competition`, `422 invalid_timezone`, `422 invalid_accent_colour`, `422 duplicate_member` (repeated or no names), `422 unknown_captain`, `422 invalid_emblem`. `timezone` defaults to the competition's. `captainEmail: null` (or the admin's own address) makes the admin the captain: the captain's name is reserved for the admin's verified email and claimed at once, in season (`membership.claimed`, feed "<name> joined the clubhouse."; `422 unverified_email` without a verified address). With another captain, `addMe: true` also adds the admin as a member outside the season, as `members/me` does, in the same transaction.
  - `PATCH /v1/admin/leagues/{leagueId}` (200 `AdminLeague`) with any of `{name, timezone, status: "active" | "archived"}` (fields left out or null are untouched; `404 unknown_league`, `422 invalid_timezone`). A rename or time zone change writes `league.updated`; archiving writes `league.archived` and keeps every row, but the league leaves every `GET /v1/me` list, its join code stops working and its league routes answer `404 unknown_league`; restoring writes `league.restored` and the feed entry "<name> is open again." (`league_restored`).
  - `POST /v1/admin/leagues/{leagueId}/captain` (200 `AdminLeague`) with `{membershipId}` appoints an active, claimed membership of that league as captain directly (`404 unknown_member` for a missing, withdrawn or other league's membership, `409 already_captain`, `409 not_claimed`). Audit `league.captain_appointed` with the old and new `captainMembershipId`; feed "<name> is captain." (`captain_appointed`). The old captain keeps their membership and loses the captain's rights.
  - `POST /v1/admin/leagues/{leagueId}/members/me` with an optional `{displayName, fullName}` adds the admin as an active member with no season membership (out of season), so writes attributed to a member work there; the name defaults to the admin's name in their most recently updated other membership, else "Admin", and the full name to the display name (`409 duplicate_member` when an active member already has that name). 201 `{memberId}` when new, audit `membership.admin_added`, feed "<name> joined the clubhouse as admin." (`member_joined`); 200 with the same id when the admin is already a member; a withdrawn membership is reinstated, still out of season (200, `membership.admin_added` with `before.status = "withdrawn"`, feed "<name> is back as admin." `member_returned`).
  - Every audit event these routes write carries `actor_label = 'admin'` and, when the admin holds an active membership in that league, its id as `actor_membership_id` (feed entries name it as the actor too).
- Competition routes live under `/v1/competitions/{competitionId}` (today only `urc-2026-27`); an unknown id is `404 unknown_competition`. Competitions are registered in `app/competitions/` (see below).
- `GET /v1/competitions` (any signed-in account): the registry, `[{id, name, shortName, timezone, regularRounds, lastRound}]`, for the management centre's league form.
- `GET /v1/competitions/{competitionId}/matches/{fixtureId}` returns the match centre for one published fixture: teamsheets from the public URC feed and the kickoff-hour forecast from Open-Meteo. Each section carries its own `status` (`ok`, `not_published`, `too_early`, `past` or `unavailable`), so a provider outage never fails the request. Weather is fetched only inside the week before kickoff, teamsheets from three days out. Responses are cached in the `piele.external_snapshots` table (weather 3 h, teamsheets 6 h once published) or in process memory when no database is configured. The fixture list comes from the competition's bundled schedule (`app/competitions/urc_2026_27/schedule.json`, written by `apps/web/scripts/import-urc.mjs`). From 15 minutes before kickoff the response also carries a `score` section: match state (`scheduled`, `live`, `half_time`, `full_time`, `postponed`, `cancelled`), minute, score, half-time score and a timeline of scoring events and cards with the running score.
- `GET /v1/competitions/{competitionId}/rounds/{round}/scores` returns the state and score of every fixture in a round (no timelines), for the fixture ribbon and hero. One URC feed query covers the whole round and is shared with the match centre through the snapshot `<competitionId>:scores:round:<n>` (every snapshot key starts with the competition id). It is cached for one minute while a match is within its play window (15 minutes before to 3 hours after kickoff), otherwise until the next kickoff window (at most 6 hours). When the URC feed fails, ESPN's public scoreboard (`ESPN_SCOREBOARD_URL`, one request per kickoff date) supplies states and scores only: `source` reads `ESPN`, the match centre's `score.timeline` is `false`, and minutes and half-time scores are null. The URC feed is then left alone for five minutes before it is tried again. On 25 September 2026 the URC feed stopped answering five minutes before kickoff and Cloudflare then blocked the polling address. A round whose first kickoff window has not opened makes no feed call and reports `too_early`. The feed rejects requests with httpx's default User-Agent (HTTP 403); the service sends its own.
- `GET /v1/competitions/{competitionId}/matches/{fixtureId}/preview` (a member of a league on that competition, or the admin; others `403 not_a_member`): the latest Pavilion preview for the fixture, or `preview: null`. Summary, key factors and mood per side, and the cited sources.
- `GET /v1/competitions/{competitionId}/rounds/{round}/updates` (a member of a league on that competition, or the admin): the round's competition events for the notifications panel, in time order: `teamsheets_published`, `preview_published` (with the revision), `kicked_off` (at the kickoff time, once the score feed shows the match under way or finished) and `full_time` (with the score). Teamsheets are looked for from three days before kickoff to two days after; the first time the API sees them published, or sees full time, it records the moment in `piele.fixture_milestones` (keyed by competition and fixture), so the times stay put while provider snapshots expire and are fetched again. Uses the same cached snapshots as the match centre, so a round's request adds no provider calls beyond what the match pages make.
- Preview agent routes under `/v1/agent`, requiring `Authorization: Bearer <PIELE_AGENT_TOKEN>` (off with 503 when the variable is unset; production requires 32 characters or more): `GET /v1/agent/fixtures/due` lists fixtures needing their preview (both teamsheets published, no preview yet, not claimed within the last 45 minutes and fewer than 3 claims; never after kickoff); `POST /v1/agent/dispatches` claims up to 8 of them in `piele.preview_dispatches` for the agent's schedule (an optional body `{fixtureId}` limits it to one fixture, and `{fixtureId, force: true}` claims that fixture even with a preview, inside a lease or after its attempts; used by the agent's `POST /previews/run`), which starts one writing session per claim, so overlapping runs never write the same fixture twice and a session that saved nothing is retried after the lease; a fixture gets one preview, which is not rewritten when teamsheets change; `GET /v1/agent/fixtures/{fixtureId}/state` returns the structured inputs (both teamsheets, changes from each side's previous teamsheet, regular starters missing, ages, bench split, rest days, travel, the kickoff forecast and hashes); `POST /v1/agent/previews` validates and stores a preview as the fixture's next revision in `piele.match_previews` (a retried `runId` returns the stored preview). Every agent request that names a fixture takes an optional `competitionId` (a query parameter on the GET routes, a body field on the POST routes) defaulting to `urc-2026-27`, and every due fixture, dispatch, fixture state and stored preview echoes it; previews and dispatches are stored with it. An unknown id is `404 unknown_competition`. See `app/agent/`. Form from recorded results waits for the results tables.

## Run locally

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```bash
cd apps/api
uv sync                      # creates .venv from uv.lock
cp .env.example .env         # works as-is without a database
uv run uvicorn app.main:app --reload --port 8000
```

Open http://localhost:8000/v1/health or http://localhost:8000/docs.

## Test

uv run pytest

## Competitions

`app/competitions/` is the registry: `ALL` maps a competition id to its `Competition` and `get(id)` returns one (KeyError when unknown). `base.py` defines `Competition` (id, name, short name, a display time zone, regular and last round, `round_label(n)`, `schedule()` loaded once from its `schedule.json`, `club(id)`, `clubs`, `stadium(name)`, `first_kickoff(n)`, `validate_round(n)`) and the `ScoresProvider`, `TeamsheetsProvider` and `FallbackScoresProvider` protocols. `urc_2026_27/` holds the URC 2026/27 instance: its schedule, club and stadium catalogue and the provider wiring (URC GraphQL scores and teamsheets, the ESPN scores fallback; the provider code stays in `app/matchcentre/providers`). A season names its competition in `piele.seasons.competition_id`; the request's actor carries it (`actor.competition`), so round bounds, round labels, spoon-duty deadlines and the favourite-team check follow the league's competition. The app holds one `MatchCentreService` per competition in `app.state.match_centres`. Adding a rugby competition is one new folder listed in `app/competitions/__init__.py`.

## Authentication, membership and evidence

Members sign in with Supabase Auth (Google or email and password) in the web app. The API verifies each access token's signature, issuer, audience and expiry (`app/league/auth.py`), then resolves the caller inside the request transaction with transaction-local row level security context (`app/league/context.py`): `account_dependency` for the account routes, `actor_dependency` for the league in the path (its active membership there, or the admin's view), `steward_dependency` for captain routes (the league's captain or the admin), `admin_dependency` for the management centre (the admin only, no league context) and `competition_member_dependency` for the member-only competition routes. An account can belong to several leagues, one membership each. It joins a league with the league's join code (`/v1/join/{code}`), choosing one of the unclaimed Superbru names. A name the captain reserved for an email (`invited_email`) is claimed automatically by `GET /v1/me`, and only for a verified sign-in with that address. The captain can release a wrong claim. Captain authority is the league's `captain_membership_id`, never a role column.

The admin (`piele.users.is_admin`, set by an operator with SQL, see docs/production.md; no route changes it) opens every active league and holds captain-level rights in all of them. Without a membership in a league the admin reads everything, and every write the schema attributes to a member (creating duties, recording standings, evidence, deciding evidence, own profile and read state) is `409 admin_not_a_member` ("Add yourself to this league from the management centre first."). Audit events of the admin acting without a membership carry `actor_label = 'admin'` and no actor membership; their feed entries have no actor. The admin creates, renames, archives and restores leagues, appoints captains and adds themselves to a league (outside the season) from the management centre, `/v1/admin` above.

Bootstrap a league with the captain's sign-in email, which reserves the captain's name; members come from `app/data/league_members.json` (Superbru nicknames as display names; its `league`, `slug` and `competitionId` are the defaults for `--name`, `--slug` and `--competition`) and join with the league's code after signing in. The command refuses to run when a league with the slug already exists. It calls `app.league.service.create_league`, which `POST /v1/admin/leagues` shares; new leagues get a random join code.

```bash
uv run python -m app.league.bootstrap --captain-email captain@example.com
uv run python -m app.league.bootstrap --captain-email other@example.com \
  --members-file other-league.json --slug pofadder-bowl --name "Pofadder Bowl" --competition urc-2026-27
```

Evidence videos go straight from the browser to a private Supabase Storage bucket (`SUPABASE_STORAGE_BUCKET`, default `evidence`) using a signed upload grant the API issues after checking membership, type and size. The API needs `SUPABASE_SERVICE_ROLE_KEY` for grants, object checks and short-lived playback URLs. Create the bucket as private in the dashboard; nothing creates it automatically.

League emblems use the same bucket under `emblems/<league id>/<token>.<jpg|png|webp>` (the migration `20260926170000_emblems_withdrawals.sql` makes `leagues.emblem_path` either `preset:<key>` or a path under the league's own prefix). The web app resizes the image to 512 px and uploads it with a grant from `POST /v1/leagues/{leagueId}/emblem/uploads`; `PUT .../appearance` checks the object and its signature, and every league description carries a signed URL valid for `LEAGUE_EMBLEM_URL_TTL_SECONDS` (default 86400). Profile photos use the same bucket under `avatars/<user id>/`; a photo is account-wide. The web app crops the photo to a 384 px JPEG and uploads it with a grant from `POST /v1/leagues/{leagueId}/me/photo/uploads`; `PUT /v1/leagues/{leagueId}/me/profile` accepts only a path under the caller's own prefix, checks the stored object's size and JPEG signature (not the uploader's type claim), and removes the replaced photo. The favourite team is checked against the league competition's club catalogue and stored on the membership (`piele.league_memberships.favourite_team_id`), so it is per league and follows the member to every device.

House marks: one mark per full 168 hours a duty stays overdue, stopping at the accepted completion time or actual season closure (`app/league/marks.py`). A challenge never pauses accrual; when one is resolved in the member's favour the captain resets the clock, which clears the elapsed time and restarts it from that moment. The API is the only calculator; the web app formats its values.

## Connect Supabase

1. Create a project at https://supabase.com/dashboard. Pick the region closest to where the Vercel function will run, and store the database password in a password manager.
2. Open **Connect** on the project page and copy the **Transaction pooler** connection string (port 6543) into `DATABASE_URL`, replacing `[YOUR-PASSWORD]`. The API uses this at runtime.
3. Copy the project URL (`https://<ref>.supabase.co`) into `SUPABASE_URL`.
4. Put these in `apps/api/.env` (uncomment the database line), run the app and check that `/v1/health` reports `"database": "ok"`.

The runtime URL should use the restricted `piele_api` role, not `postgres`. The migration creates the role without a password. Enable it once per project in the SQL editor with `alter role piele_api with login password '<generated>';`, then connect through the pooler as `piele_api.<project-ref>`.

`sslmode=require` encrypts without checking the server certificate. To verify it, add the query parameters `sslmode=verify-full&sslrootcert=certs/supabase-prod-ca-2021.crt`. The relative path resolves against this directory.

## Migrations

Schema changes are SQL files in the repository root's `supabase/migrations/`, the single migration history. The Supabase GitHub integration applies them to the linked project on pushes to the connected branch; nothing runs at API startup. Application tables live in the private `piele` schema, which must stay out of the Data API's exposed schemas. The first migration, `20260923184500_external_snapshots.sql`, creates the provider cache table.

To apply migrations by hand, install the Supabase CLI and run `supabase link` then `supabase db push` from the repository root.

## Deploy to Vercel

1. In Vercel, choose **Add New > Project** and import this repository.
2. Set **Root Directory** to `apps/api`. Vercel detects FastAPI from `pyproject.toml`, installs dependencies from `pyproject.toml` and `uv.lock`, and loads `app` from `app/main.py`. No `vercel.json` or `requirements.txt` is needed.
3. Under **Environment Variables**, set:
   - `ENVIRONMENT` (`production` or `staging`). `production` refuses to start without HTTPS `ALLOWED_ORIGINS` and `DATABASE_URL`, and hides `/docs`.
   - `ALLOWED_ORIGINS`: the exact Angular origin(s), e.g. `https://pavilion-web.vercel.app` once the Vercel project is renamed (`https://piele-web.vercel.app` before)
   - `DATABASE_URL`: the transaction pooler string (port 6543)
   - `SUPABASE_URL`
   - `SUPABASE_JWT_AUDIENCE` only if it differs from `authenticated`

   Give Preview a staging Supabase project, not production credentials.
4. Deploy, then open `https://<deployment>/v1/health`. For production, follow [docs/production.md](../../docs/production.md).
