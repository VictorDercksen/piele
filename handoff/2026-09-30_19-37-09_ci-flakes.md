# CI flakes on PR #80: artwork warm-up leak and the captain picker

## Request

PR #80's `web` job failed twice on the same commit, each time in a test the PR does not touch. The user chose to fix both in the PR.

## Changes

- `core/competition/match-artwork.ts`: `warm()` now keeps a cancel for each warm-up waiting on an idle browser (`whenIdle`, `requestIdleCallback` or a 200 ms timeout) and cancels them when the service's injector is destroyed.
  - Cause: Vitest runs the specs non-isolated in one jsdom. A fixture ribbon from an app or shell spec left a warm-up timer running after its test bed was torn down. On a slow runner it fired inside `match-artwork.spec`'s warm-up test and loaded a round's images through that test's stubbed `decode` (CI: 53 decodes counted where 7 were expected).
  - Reproduced with a throwaway spec (13 decodes where 7 were expected) before the fix.
- `match-artwork.spec.ts`: new test, "drops a warm-up still waiting when the app is torn down". It fails without the fix (7 decodes) and passes with it.
- `e2e/support.ts` `chooseOption`: open, fill and pick now retry together (`toPass`, 3 s per step, 20 s overall).
  - Cause: in CI the captain picker's popup closed after the test saw it open. The search input was detached and never came back, so `fill` timed out.
  - Could not reproduce locally, even at 20× CPU throttle, so the root cause of the popup closing is unknown.

## Checks run

- `ng build` (Node 24): success, no warnings.
- `ng test --watch=false`: 115 files, 570 passed.
- Playwright full suite: 73 passed.

## Unresolved / next steps

- Why the captain picker's popup can close on its own on a slow machine is not known. If it can happen to users, it is worth investigating in `shared/search-select`.
